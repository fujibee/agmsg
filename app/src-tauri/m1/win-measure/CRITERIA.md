# Setting WINDOWS_VERIFIED = true: pass criteria

`WINDOWS_VERIFIED` (in `src/addons/gate.rs`) turns add-ons on for Windows. It is flipped in one commit, only when every item below holds for the same candidate head. Reviewers check the items against the evidence (CI runs and the returned `summary.txt`); anything not shown counts as not met.

## Evidence required

1. **Windows unit tests.** The `addons-windows` workflow is green at the candidate head (links, hard links, 8.3 names, junctions, case, denylist, real server on Windows paths).
2. **Verdict logic and process rules.** `selftest.sh`, `selftest-procs.sh` and `selftest-sink.sh` pass in the `win-measure` workflow. `selftest-procs.sh` proves the run script exits without a single `taskkill` when another run's executables are present, stops only the process ids it launched (never by image name), leaves a reused id alone, refuses a package with macOS `._*` files or without `builtin-addons/`, and does not inventory anything outside the package. `selftest.sh` feeds made-up logs to the same functions the run uses: a frame that loaded and said nothing, another step's violation, a report-only violation, a missing record, an app-origin navigation that was allowed or completed (even when the pane says it is alive), and a blob:/data: frame matched by another address or an ambiguous step must all FAIL. `selftest-sink.sh` proves the sink's final count counts only when the sink confirmed it with the run's token (a stale value, a dead or killed sink, another token or a count above the control all FAIL), that the archive gets its final name only when `tar` finished, and that the run ends once, whatever the exit.
3. **Product build.** The `win-measure` workflow built that same head (the artifact's `BUILD-INFO.md` names the commit and the sha256 of both executables; the run used those hashes). The package was made without macOS metadata (`tar` with `COPYFILE_DISABLE=1`; no `._*` member) and carries `bin/builtin-addons/{fileview,diffview}` next to the executables.
4. **Run on a real Windows machine** with `run-win.sh`, inside an Active desktop session (`session.log` shows the session Active at the start and end of every step). `summary.txt` has no `FAIL` line and these `PASS` lines:
   - `S0` an Active session exists; `GUARD` the recorded snapshot of the real agmsg home is unchanged after the run: the sha256 of the installed scripts, `SKILL.md`, `VERSION`, `uninstall.sh` and the `types`, `templates` and `plugins` folders, the top-level listing of the install, the list of skills, the Claude commands, and whether the run's team name appears among the real teams (before and after files and their diff are in the output folder). It is not a byte-for-byte comparison of the whole home folder (the run never runs install.sh and never changes HOME). `summary.txt` ends with the `archive:` line and the archive's `.tgz` exists.
   - `S1-debug`, `S1-release` and their `-builtins` lines: both built-in add-ons were found and match their digests, the startup check ends with only the "not verified" reason, and the frame guard was installed. That means, on the product build itself: the probe frame is opaque and under the pane CSP, a navigation to the app origin was refused (on Windows the probe's final answer is missing after the cancel; the document may have been replaced: the guard's own record of the exact cancelled target, together with the enforced `frame-src` violation for it, stands in for the surviving document), WebRTC is absent, and the UDP sentinel received nothing.
   - `S2`, `S3-driver`, `S3-answers`, five `S3-positive` lines: the built-in File view and Diff view open, are granted a throwaway folder, and answer every permitted read; every refused request is refused with the expected code.
   - `S3-nav-*` for all five self-navigations (tauri://, http://tauri.localhost, https://tauri.localhost, location.replace, meta refresh). On macOS: the pane is still itself three seconds after the attempt. On Windows (where the guard's log lines exist): in that case the guard refused, at its start, a frame navigation to the app origin, and in the whole log no navigation to the app origin was allowed or completed successfully (an allowed or completed one fails every case, whatever the pane reports). The pane itself does not report after the attempt on Windows (its document may have been replaced), so the guard's record is the evidence.
   - WebRTC, in every realm a pane can reach: `S3-realm-*` for the first script of the pane page (before anything else ran), the pane page, a srcdoc child, a nested child, an about:blank child, a blob: child, a data: child, a dedicated worker and a shared worker. Each passes only if a script ran there and found no WebRTC name, or if the evidence shows no script can run there (the frame never loaded and the app logged the refused navigation; an enforced `frame-src`/`worker-src`/`script-src` report naming the address; on Windows, for blob:/data: frames, an enforced `frame-src` report whose address is empty (the engine gives none), every enforced report of the step being empty, and exactly one frame navigation of the step seen and refused by the guard; a worker that failed to start; an unreachable about:blank document). For the nested child the evidence is its parent: the srcdoc child was refused (never loaded and the navigation was refused in its step), so no script could run in it to create the nested one; if the parent ran, the nested child must itself pass. A realm that loaded and said nothing, or that exposes any WebRTC name, fails. `S3-sink-hits`: a local UDP+TCP sink received nothing from the panes. It is judged only by the sink's final acknowledgement for this run's token (`<token> udp=1 tcp=1`, the control alone), never by the live counter file; `S3-sink-control` proves the sink counts and `S3-sink-start` that it could listen.
   - Egress: `S3-egress-*` for the sink, LAN-like and public addresses over fetch, XHR, WebSocket, EventSource, beacon and image: each attempt was refused and has its own enforced `connect-src`/`img-src` report naming that address (or was refused before any request, `threw SecurityError`); `S3-eval` (eval refused), `S3-net-finished`.
   - `S1-release-switch`: the release build with `AGMSG_WINDOWS_MEASURE=1` still reports the not-verified reason (the measuring switch is compiled out).
5. **Twice.** Two complete runs, each passing item 4 (a flaky pass is not a pass). Both on a machine whose WebView2 Runtime version is recorded in `s0-env.log`.
6. **Review.** The two reviewers have cleared the candidate head, including `nav_win.rs` (required, fail-closed frame guard) and `no_webrtc.js` plus its wiring in `host.rs`.

## Flip and re-check

7. The flip commit changes the product's behaviour only through `WINDOWS_VERIFIED`. Its comments and the expectations of the gate tests that assert the old value change with it; nothing else changes behaviour. A new `win-measure` build of that commit is run once more with `EXPECT_VERIFIED=1`: `S1-debug` and `S1-release` must show `enabled=true`, and the rest still passes.
8. The debug-only measuring switch (`AGMSG_WINDOWS_MEASURE`) stays debug-only: after the flip, `S1-release-switch` is kept as a check that the switch has no effect in the release build (the not-verified reason cannot come back, and nothing else can be waived).

## Not claimed

The run covers the Windows and WebView2 versions of the test machine only. It shows that the guard refused the frame navigations of the five chosen self-navigation cases and the probe, and that no navigation to the app origin was allowed or completed in the logs of the runs; it does not show that no path can commit an app document in a pane frame. Other defences were not measured by the run: `window.open` is denied by the host (`on_new_window`), navigation of the top page is blocked by the frame's `sandbox="allow-scripts"` only, and history, form submission and reload were not tried. What the replacement document of a refused frame is (an error page) is not shown either. The installer build is not measured: the package is a plain `cargo build` with the built-in add-ons copied next to the executables. A WebView2 Runtime that cannot supply the frame events fails the guard setup and turns add-ons off by itself (the gate shows why); that behaviour is covered by unit tests, not by the run.
