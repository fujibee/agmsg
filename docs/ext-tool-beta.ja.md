# ext-tool — 外部のプログラムをチームのメンバーにする

*[English](ext-tool-beta.md)*

`ext-tool` は、中身が CLI のエージェントではなくプログラムであるエージェントの種類。
ほかのメンバーと同じようにチームに join し、そのメンバー宛てのメッセージが、そのまま
呼び出しになる。チームのやりとりが、そのままインターフェースになる。

> ⚠️ **実験中。インターフェースも作りも変わる。**
> ext-tool を先に出しているのは、アダプタとの約束を本物のツールで試すため。
> 2つはもう決まっていて、あとから入る: メッセージの配達はデーモン（`agmsgd`）が持つ
> ようになり、ここに書いてある呼び出しは、送信コマンドがやることではなく、そのデーモン
> が持つ*配達の一種*になる。このページのパスもオプションも、まだ固まっていないものとして
> 読んでほしい。
>
> **外部からのアダプタの取り込みは、まだ受け付けていない。**
> つなぎたいツールがあれば、課題として書いてほしい（その声が約束の形を決める）。ただし
> プルリクエストは、このページから警告が消えるまで待ってほしい。

## なぜツールの呼び出しではなく、メンバーなのか

ツールの呼び出しは、1つのエージェントのセッションの中の出来事になる。ほかのメンバーには
見えず、チームの履歴にも残らず、ランタイムごとに別々に設定することになる。メンバーには
宛先がある。

- **やりとりが記録に残る。** 依頼も返事も、ふつうのメッセージ。チームの誰でも（あとから
  読む人間も含めて）、何を頼んで何が返ってきたかを見られる。
- **1つの宛先で、どのランタイムからも。** Claude Code でも Codex でも、ほかの席でも、同じ
  名前に送る。ランタイムごとに入れるものはない。
- **鍵が1か所にある。** 鍵はそのメンバーの設定にあり、各エージェントの設定には置かない。
- **呼ぶのではなく、任せる。** 送った側は待たない。アダプタが時間をかけてよく、返事は
  メッセージとして届く。
- **人もプログラムも、同じ宛先の空間にいる。** 人が集まっているチャンネルも、判断を返す
  モデルも、どちらもメンバー。

## ツールを join する

```bash
bash <skill-root>/scripts/join.sh <team> <name> ext-tool --tool <tool>
```

`<skill-root>` は agmsg が自分を入れた場所。既定では `~/.agents/skills/agmsg/` で、
インストール時に別のコマンド名を選んだ場合は `~/.agents/skills/<名前>/` になる。
PATH に `agmsg` コマンドはまだ無い（#1353）ので、このページのコマンドはすべて
スクリプトの場所で書いてある。

アダプタは `scripts/drivers/ext-tools/<tool>/` の下にある。同梱は2つ。`slack`（決めた
チャンネルに投稿する）と `jev`（OpenRouter 経由で TypeSafe の Jev に、型のついた判断を
聞く）。

そのメンバーの設定がまだ無ければ、`join` は断って、アダプタの `SETUP.md` の場所を出す。
このファイルは、キーボードの前にいるエージェントに向けて書いてある。アプリを作り、入れ、
鍵を保存し、本物に1回つないで確かめるまでを、1歩ずつ案内する。設定のコマンド自体は
何も聞いてこないので、同じ手順が人の手でも CI でも通る。

```bash
bash <skill-root>/scripts/ext-tool.sh setup  <team> <name> <tool> status|check <item>|save|test
bash <skill-root>/scripts/ext-tool.sh secret <team> <name> [--from-clipboard]
```

`secret` は、端末から値を読む。エージェントに端末を渡せないときは、クリップボードから
読む。権限 600 で書き、返すのは書いた場所だけ。値は、チャットにも、メッセージの履歴にも、
ログにも出ない。

## そのメンバーへの頼み方

アダプタごとに `USAGE.md` がある。読む相手は、そこに送る側のエージェント。そのメンバーが
何をするか、どんな形を受け付けるか、そのまま貼れる例、何を断るか、そして「形が正しい」
だけでなく「良い答えが返る」ための知識が書いてある。最初の1通を送る前に読む。

```bash
bash <skill-root>/scripts/ext-tool.sh usage <team> <name>
```

断るときも同じ文書を指す（いまはパスで、`drivers/ext-tools/<tool>/USAGE.md`）。形が
違っていても、1往復で直せる。

アダプタは、自分がどれくらい厳しいかを `tool.conf` で宣言する。

- `request=strict` — 本文がそのまま呼び出しになっていること。アダプタは解釈せず、断って
  `USAGE.md` を指す。`jev` は厳しいほう。速くて安いことが取り柄だから。
- `request=loose` — ふつうの文章での依頼でよい。`slack` はこちら。

## アダプタとの約束

アダプタは、実行できるものなら何でもよい。agmsg とのやりとりは、標準入力・標準出力・
終了コードの3つだけ。

| | |
|---|---|
| 標準入力 | JSON 1個: `team`, `from`, `to`, `body`, `message_id`, `config_path` |
| 標準出力 | 返事の本文。空なら「返事を送らない」 |
| 終了コード 0 | 成功 |
| 終了コードが 0 以外 | 失敗。agmsg が、名前つきの1行を送り主に返す |
| 時間の上限 | `tool.conf` の `timeout=`。超えたらプロセスのグループごと止めて、送り主に伝える |

それ以外は、すべてアダプタ自身の裁量。`tool.conf` が必要な設定の項目を宣言し、`setup` が
確かめて保存し、`SETUP.md` が「人をどう案内するか」をエージェントに教える。

失敗が黙って消えることはない。設定が無い、知らないツール名、時間切れ、0 以外の終了、
どれも1行になって送り主に返る。

## 同梱のアダプタ

**`slack`** は、本文を、決めた1つのチャンネルに投稿する。返事は空（投稿するだけ）。
`setup test` は本物のメッセージを1通投稿して、その投稿へのリンクを返す。Slack 側の
返信を agmsg に戻すことは、まだできない。

**`jev`** は、型のついた質問を投げて、1行で答える。例:

```
jev: sonnet / high (choice p=0.96, confidence=0.94, cost $0.000021)
```

質問はメッセージと一緒に届く。本文が JSON で `questions` を持っていれば、それがそのまま
渡るので、エージェントは必要な判断をその場で組み立てられる。うまく聞くための書き方は、
アダプタの `USAGE.md` にある。選択肢を分けるために測って決めた言い回しや、質問自身の
`instructions` と `criteria` を日本語で書いた回では確率が割れたままだったのに対し、英語の
言い回しでは分かれた、という実測も載せてある。

## この版でできないこと

- **このマシンから送ったメッセージだけが、アダプタを動かす。** 同期で届いたメッセージでは
  動かない。いまは呼び出しが送信の経路にぶら下がっているため。デーモンがこれを引き取る、
  いちばんの理由がこれ。
- **アダプタは、送った人のマシンで動く。** そのメンバーを join したマシンではない。外の
  サービスに投げるだけのツールなら違いは出ないが、手元のものに触るツールでは出る。
- **1つのツールは1つのインストールで、というのは運用の決めごとで、仕組みではない。**
  いまは送った側のインストールだけがアダプタを動かすので、1台から送れば1台でだけ動く。
  配達がデーモンに移ると、2つのインストールで join されたツールは両方で動く。別々の
  インストールは別々の世界で、突き合わせる仕組みは無いから。1つのツールは1か所で join
  してほしい。排他の仕組みは、あとで考える話であって、この版の約束ではない。
- **ツールから話しかけることはできない。** アダプタは答えるだけで、自分から会話を始め
  ない。Slack の返信をチームに戻すには、これが要る。
- **再試行も、順番の保証もない。** 失敗した呼び出しは報告されるだけで、やり直さない。
- **その場で答えを受け取る呼び方はない。** 同じコマンドの中で答えが返ることはなく、返事は
  メッセージとして届く。

## これからどうなるか

`agmsgd` が配達を持つと、アダプタを呼ぶことは、メンバーにメッセージを届ける方法の1つに
なる。Claude Code の席に流すのも、端末に打ち込むのも、同じ層の話になる。そうすると、上に
並べた制限は「特別な事情」ではなく「配達の性質」として片付く。同期で届いたメッセージも
ふつうに配達され、1つのインストールの中で同じ1通が2回走ることはなく、再試行も順番も、
失敗の打ち切りも、配達のループが持つ。片付かないのは、同じツールを2つのインストールで
join した場合だけ。そこはチームの組み方の話として残る。

**上に書いたアダプタとの約束は、この移行を越えて変わらないようにしてある。** 呼ぶ側は
変わるが、標準入力・標準出力・終了コード・時間の上限は変わらない。

同じ線から、設計の決めごとが2つ出てくる。

- **アダプタがモデルを呼ぶのは、1回まで。** 自然文の依頼を具体的な API の呼び出しに直す、
  生の結果を読める1行にする、といったことはモデルの仕事で、画面を持たない1回の呼び出しで
  足りる。ツールごとに任意で、上限つき。
- **メッセージをまたいで文脈を持つものは、ツールではなく席。** 前のやりとりを覚えている
  必要がある、自分でやり直す、何ターンも判断を重ねる、という仕事なら、エージェントを
  立ち上げる。ext-tool は「1通もらって、1通返す」にとどめる。

## MCP との関係

MCP と ext-tool は、別の問いに答えている。MCP は「1つのエージェントが、どうツールを
呼ぶか」。ext-tool は「チームに誰がいるか」。この2つは組み合わせられる。両方やる予定で
（#1354）、MCP を話す汎用のアダプタ（既存のサーバーがそのままメンバーになる）と、その
上に乗る名前つきのアダプタ（自分の語彙と設定の案内を持つ）の2層になる。どちらもまだ
実装していない。

いま MCP が先を行っていて ext-tool に無いもの: 標準のスキーマ、発見のしくみ、そして既に
ある大量のサーバー。だからこそ、言い直すのではなく、そこから借りる。
